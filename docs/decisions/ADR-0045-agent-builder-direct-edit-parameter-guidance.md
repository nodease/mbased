# ADR-0045: Agent Builder direct edit and parameter guidance

Status: Accepted

Related ADRs: [ADR-0019](ADR-0019-agent-builder-preview-apply-save-boundary.md), [ADR-0024](ADR-0024-agent-builder-node-capability-catalog.md), [ADR-0025](ADR-0025-agent-builder-intent-model-selection.md), [ADR-0026](ADR-0026-agent-builder-intent-and-connection-validation.md), [ADR-0027](ADR-0027-agent-builder-pre-intent-safe-kb-context.md), [ADR-0040](ADR-0040-agent-builder-unified-model-recommendation.md), [ADR-0046](ADR-0046-agent-builder-graph-mutation-and-cas-save.md), [ADR-0054](ADR-0054-agent-builder-generation-modes.md)

## Context

Agent Builder MVP는 서버가 draft preview를 만들고 사용자가 `적용 및 저장`을 선택한 뒤에만 workflow graph를 변경한다. 이 경계는 저장 전 권한 재확인과 stale 검사를 명확하게 만들지만, graph 생성과 node 설정을 한 번에 확정해야 하므로 다음 문제가 생긴다.

- 설정이 부족한 node를 만들기 위해 여러 종류의 clarification이 Agent Builder message 계약에 계속 추가된다.
- parameter의 정의, 입력 UI, graph 연결 추천이 planner 응답과 frontend 조건문에 분산된다.
- 사용자는 preview와 실제 editor를 오가며 node를 확인해야 하며, 생성 직후 기존 node panel에서 값을 채우는 흐름과 단절된다.
- parameter마다 자연어를 다시 구조화하면 비용과 지연이 커지고, catalog와 runtime 계약보다 LLM 추론이 우선될 위험이 있다.

Workflow editor에는 graph snapshot 기반 Undo/Redo가 이미 있다. Node Capability Catalog도 node 지원 여부, 연결 정책, 필수 설정을 제공한다. 따라서 Agent Builder가 안전한 `GraphMutation`을 만들고 editor가 이를 하나의 history transaction으로 적용한 뒤, catalog 기반 parameter task를 순차 처리하는 구조가 더 응집도가 높다.

## Decision

MBA-228은 다음 목표 구조를 채택한다.

1. Agent Builder direct-edit는 설정을 확인하며 만드는 흐름과 구조만 생성하는 흐름을 지원한다. MBA-228 당시 mode 값은 `configure_and_generate|structure_only`였으며, 현재 canonical mode와 기본값, 빠른 생성 eligibility 및 mode 전환은 ADR-0054가 소유한다.
2. planner LLM은 사용자 요청을 한 번 구조화해 node 목적, graph 의도, parameter가 필요한 이유에 대한 안전한 설명을 만든다. Parameter 설명 hint는 `step_id`, Catalog가 prompt에 제공한 `parameter_key`, `reason`, `input_guidance`로 제한한다. Backend는 step capability의 Catalog에 존재하는 key만 사용하고 잘못된 hint는 폐기한 뒤 Catalog 설명으로 fallback한다. 실제 parameter key, 타입, 필수 여부, 검증 규칙은 Node Capability Catalog가 결정한다.
3. backend는 완성 graph snapshot 대신 base graph hash와 workflow `updated_at`을 전제로 한 typed `GraphMutation`과 parameter task 목록을 반환한다.
4. frontend editor adapter는 Agent Builder 시작 전 graph snapshot과 acknowledgement가 끝난 최종 graph를 하나의 Workflow history boundary로 관리한다. 최초 `initial_graph`, `graph_edit` 또는 `replace_workflow`가 boundary를 만들고 이후 `parameter_update`와 `knowledge_binding`은 graph를 CAS 저장하되 별도 Workflow history entry를 만들지 않고 같은 boundary의 final snapshot/hash만 갱신한다. 생성 완료 뒤 수동 editor 변경은 일반 history entry로 boundary 뒤에 쌓이므로 먼저 Undo된다.
5. `설정하며 생성`에서는 catalog에 정의된 모든 configurable parameter에 task record를 만들고 graph topology 순서의 node별 카드 그룹으로 표시한다. 최초 structural GraphMutation이 acknowledgement되기 전에는 group을 `pending_save|pending_ack`로 잠그고 decision endpoint 제출과 완료 UI를 차단한다. Acknowledgement 뒤 안전한 자동 추천값은 `resolution_source=user_request|existing_graph|upstream_selector|catalog_default`와 recommendation fingerprint를 가진 `completed` 요약으로 표시하고, 첫 미설정 task만 `active`로 전환한다. 단, 새 LLM node의 `auto_model_routing`이 Catalog 기본값 `false`인 경우 기능 비활성화를 사용자 결정 없이 확정하지 않고 추천값이 채워진 `active` 확인 task로 유지한다. 사용자가 `false`를 그대로 확인하면 graph 저장 없는 `confirm`, `true`로 변경하면 `set -> parameter_update -> CAS 저장 -> acknowledgement`를 사용한다. 사용자가 완료 추천의 `수정`을 열면 같은 task의 `set` action이 새 `parameter_update` GraphMutation, CAS 저장과 acknowledgement를 거쳐 값을 갱신한다. 현재 입력 task의 node를 canvas 중앙에 focus하고, 값은 일반 chat message가 아닌 타입별 control로 입력한다. 그 밖의 기존 session active 추천 `confirm`은 호환 경로로만 유지한다.
완료된 persisted ParameterGroup을 session read에서 복구할 때도 현재 Catalog task를 `node_id + parameter_key` identity로 병합한다. 기존 task의 상태, version과 순서는 보존하고 신규 task만 추가한다. 신규 task가 현재 graph에서 자동 확정되거나 숨겨지지 않고 사용자 입력을 요구하면 첫 task만 `active`로 만들고 group을 `completed`에서 `active`로 되돌린다. 같은 session을 반복 조회해도 task를 중복 생성하지 않으며 `agent_builder_task=false` parameter는 병합하지 않는다.
6. 이전 node의 output과 현재 node의 input 계약에서 만들 수 있는 selector는 deterministic resolver가 추천한다. LLM이 임의의 JSON path나 credential 값을 생성하지 않는다. LLM prompt가 참조하는 runtime 변수 이름은 canonical `referenced_variables[].name`이며 현재 문법은 `{{변수명}}`이다. 기존 selector를 다시 저장할 때는 기존 이름을 보존하고 새 selector는 Catalog output key를 이름으로 사용한다. 같은 LLM 안에서 중복 이름은 runtime context 덮어쓰기를 막기 위해 저장 전에 거부한다. 기존 graph 수정의 `between` 요청은 선택된 edge 또는 자연어로 식별한 source/destination node 쌍만 대상으로 한다. 자연어 node 쌍은 server-loaded graph의 직접 edge가 정확히 하나일 때만 삽입 위치로 확정한다. 직접 edge가 없거나 둘 이상이면 임의 선택하지 않고 기존 edge 선택 clarification으로 닫는다. 여러 hop 경로 탐색은 이 ADR의 범위가 아니다.
7. `구조만 생성`은 `generation_mode=structure_only`로 표현하고 parameter task를 열지 않는다. 빈 workflow의 신규 생성은 `initial_graph`, 기존 workflow의 부분 구조 변경은 `graph_edit`, 비어 있지 않은 editor에서 완결된 신규 workflow를 생성하거나 명시적으로 전체 교체하면 `replace_workflow` GraphMutation을 사용한다. `replace_workflow`는 기존 edge/node 전체를 제거하고 새 node/edge를 추가하는 typed operation 묶음이며 raw graph payload를 허용하지 않는다. Generation mode와 mutation kind는 독립이고 unresolved external-action configuration은 실행·배포 preflight가 계속 차단한다.
8. Knowledge Base 선택, 자동 추천 확인과 수동 parameter 입력은 하나의 workflow 설정 결과 UI에서 순차 처리한다. 같은 Knowledge requirement에 legacy clarification과 direct-edit 설정 card를 동시에 표시하지 않는다. Knowledge Base 선택이 node 종류나 graph topology를 바꾸면 통합 UI의 첫 단계인 `before_graph`, 기존 node binding만 바꾸면 graph 생성 뒤 같은 UI의 `after_graph`로 처리한다. `before_graph` 후보를 하나도 선택하지 않은 제출은 별도 가짜 후보나 재질문 없이 KB 없이 생성하겠다는 명시적 결정이다. Direct response의 `knowledge_resolution`은 후보 유무와 무관한 상위 `resolution_id`를 가지며 candidate가 처음부터 0개여도 같은 설정 card와 empty-selection CTA를 표시한다. Planner는 선택별 완성 graph를 만들지 않고 requirement id, timing, target step, effect kind와 Knowledge step/upstream/downstream/empty-selection bridge policy로 구성된 typed Knowledge placement만 반환한다. Backend는 KB와 무관한 base topology와 이 placement를 Catalog로 검증한 뒤 선택이 있으면 Knowledge 의존 node/data/edge를 구성하고 빈 선택이면 bridge policy에 따라 이를 생략한다. 여러 KB는 같은 requirement의 binding 목록으로 처리하며 선택 뒤 자연어 요청이나 planner를 다시 호출하지 않는다. 선택 graph와 KB-free graph 중 해당 제출 결과가 유효하지 않으면 부분 저장 없이 validation failure로 닫는다.
9. raw secret, token, API key, credential config는 planner prompt, 일반 chat transcript, parameter task 설명, task/session persistence, audit metadata에 포함하지 않는다. Mail/Gmail처럼 관리 credential resource가 있는 node는 safe credential reference만 허용한다. Slack Bot Token, Slack Incoming Webhook URL과 GitHub API Token처럼 기존 node graph가 직접 소유하고 기존 Editor 저장 경로가 지원하는 `secret` parameter는 Agent Builder task와 masked input card로 제공한다. 기존 값의 원문은 hydrate하거나 표시하지 않고 새 입력 또는 명시적인 삭제만 허용한다. Raw secret은 일반 ParameterDecision, GraphMutation operation envelope, Agent Builder session/task payload 또는 audit/log/trace에 넣지 않으며 frontend editor adapter가 기존 node data 저장 경로에 직접 반영한 뒤 canonical draft metadata 변경과 session reconciliation로 완료 상태를 확인한다. Agent Builder 전용 credential resource나 별도 secret 저장소는 만들지 않는다.
10. graph 생성 중 workflow 실행, retrieval, 외부 action 실행, credential 사용 또는 외부 시스템 변경은 발생하지 않는다.
11. 최초 graph 생성, 기존 graph 구조 변경, 전체 workflow 교체, parameter decision과 `after_graph` Knowledge binding은 ADR-0046의 공통 `GraphMutation`을 사용한다. Local 적용 뒤 `operation_id`, expected base graph hash와 expected workflow `updated_at`을 포함한 CAS workflow draft 저장을 수행하고, server가 반환한 canonical graph hash와 `updated_at`으로 acknowledgement한다. Agent Builder 저장, 일반 autosync, version 복원, test 전 저장과 Undo/Redo는 같은 frontend canonical metadata 상태를 읽고 모든 성공한 draft GET/POST 결과로 이를 갱신한다. Server는 acknowledgement 전에는 operation, parameter task 또는 Knowledge selection을 완료하거나 다음 task를 활성화하지 않는다.
12. MBA-228 parameter/input/output 계약은 Workflow Node Capability Catalog v3로 도입한다. Phase 1에서 단일 bundled catalog, parser와 backend/frontend parity test를 함께 v3로 전환한다. Full typed `operations`는 발급 API 응답에서만 client에 전달하고 DB/session payload에는 저장하지 않는다. 기존 `AgentBuilderRequest.response_payload`에는 `catalog_version=3`, operation id/kind/status, base graph hash, 발급 시 server가 candidate를 검증해 계산한 `expected_result_graph_hash`, expected workflow `updated_at`, affected node ids와 completion context로 구성된 safe operation envelope만 저장한다. 버전이 없거나 `2`인 미적용 operation은 legacy stale로 분류해 재생성을 요구하며, `3`인 envelope만 CAS 저장·acknowledgement 후보가 된다. Catalog version이나 operation 원문을 위한 별도 column/table, encrypted operation store 또는 legacy backfill은 만들지 않는다.
13. Direct-edit는 MBA-228의 단일 기능 PR에서 additive protocol migration과 mixed-version read로 전환한다. Nullable `AgentBuilderSession.protocol_version`을 추가하고 신규 direct-edit session에는 `direct_edit_v1`을 기록한다. 기존 null session은 backfill하거나 자동 변환하지 않고 legacy Preview session으로 판별해 `stale_protocol`로 복구한다. Preview API/UI는 direct-edit parity와 필수 integration/E2E 검증을 통과한 뒤 제거한다. `generation_mode`는 request마다 선택할 수 있으므로 request `response_payload`에만 저장한다. MBA-228의 기존 `configure_and_generate` 값은 ADR-0054에 따라 canonical `guided_generate`로 읽기 정규화하며 기존 row를 backfill하지 않는다. Frontend와 Gateway의 무중단 전환, 단계적 rollout/rollback, 배포 gate와 image 산출물 분리는 별도 배포 결정의 범위다.
14. GraphMutation의 `configuration_state=unresolved` 외부 action node는 저장할 수 있지만 server-side 실행과 배포 preflight에서 차단한다. Mutation 발급, CAS 저장, 차단과 acknowledgement는 safe metadata만 audit한다.
15. 모든 graph 저장과 acknowledgement가 완료되어 Agent Builder 결과가 완료 상태가 된 뒤 Workflow Undo가 boundary에 도달하면, configurable ParameterTask가 있는 경우 첫 Undo는 graph를 바꾸지 않는 parameter 재진입 단계다. 재진입 대상은 수동 설정 여부와 관계없이 `completed|skipped|deferred` 중 재편집 가능하고 `stable_order`가 가장 큰 task다. 이때 persisted task status/version과 graph 값은 변경하지 않고 client presentation에서만 해당 task를 현재 편집 대상으로 표시한다. Agent Builder panel이 닫혔거나 최소화돼 있으면 열고 최소화를 해제하며, 대상 node를 선택해 panel을 제외한 가시 canvas 영역에서 가리지 않는 가장 큰 배율로 focus하고 해당 card를 보이게 scroll한다. 첫 Undo 직후 input control로 keyboard focus를 강제하지 않아 다음 canvas Ctrl+Z가 전체 복구로 이어질 수 있게 한다. completed/skipped/deferred task 사이의 이동은 Workflow Undo가 아니라 ParameterTask UI의 `이전 항목` control이 담당한다. 재진입 상태에서 다음 Workflow Undo는 Agent Builder 시작 전 snapshot을 CAS 저장하고 생성 node/edge, parameter 값과 Knowledge binding을 포함한 결과 전체를 제거하며 모든 ParameterTask와 Knowledge resolution을 `canceled`로 닫는다. Task가 없으면 완료 상태의 첫 Undo가 바로 전체 복구다. `replace_workflow` boundary의 시작 snapshot은 교체 전 graph 전체다. Graph 저장 또는 acknowledgement가 끝나지 않은 결과는 완료 상태 Undo로 취급하지 않는다.
16. 전체 복구 뒤 reload 전 Ctrl+Y 또는 Ctrl+Shift+Z는 client memory의 최종 graph snapshot을 다시 적용하고 서버 graph를 CAS 저장하지만 canceled ParameterTask나 Knowledge 흐름을 재실행하지 않는다. 전체 Redo 뒤 같은 client memory에서 다시 Undo하면 canceled task UI에 재진입하지 않고 시작 전 graph로 바로 CAS 복구한다. Parameter 재진입 단계에서 Redo는 graph를 바꾸지 않고 설정 UI를 닫아 완료 표시로 돌아간다. Redo stack과 parameter 재진입 표시는 client memory 전용이며 reload 뒤 복구하지 않는다. Parameter input의 Ctrl+Z는 control 내부 text history만 사용하고 Agent Builder card/button focus에서는 canvas Undo/Redo command를 실행하지 않는다.
17. Catalog v3의 각 parameter는 `defer_policy=forbidden|allow_unresolved`를 가진다. 값이 없으면 `forbidden`으로 해석한다. Required parameter의 `forbidden`은 frontend에 defer control을 제공하지 않고 backend도 defer를 거부한다. `allow_unresolved` defer는 `parameter_update` GraphMutation, CAS 저장과 acknowledgement 뒤 task를 `deferred`로 전환하고 다음 task로 진행한다. Optional `skip`은 defer와 별도이며 graph 값을 만들지 않고 operation id와 expected task version 검증 뒤 task를 명시적 `skipped` 상태로 전환한다. LLM의 system/user/assistant prompt가 모두 비어 있으면 세 task를 순차적으로 확인하며 앞의 두 빈 prompt는 건너뛸 수 있지만 마지막 남은 빈 prompt는 건너뛸 수 없다. 세 prompt 중 하나가 canonical graph에 유효하게 저장된 뒤에만 나머지 prompt skip을 허용한다. Skipped task를 다시 열어 값을 설정하면 일반 `parameter_update`/CAS/acknowledgement를 거쳐 `completed`가 된다. Parameter flow 전체 취소는 남은 task를 `canceled`로 닫고 이미 저장된 graph는 유지한다. Node `configuration_state`는 마지막 task action이 직접 지정하지 않는다. Backend가 Catalog의 모든 required configuration을 생성, set/defer/skip/Undo/복구와 실행·배포 preflight마다 다시 계산하며 하나라도 missing/deferred/invalid이면 `unresolved`, 모두 유효할 때만 `resolved`다. Client가 이 값을 권위 있게 설정할 수 없다.
`_deferred_parameters`에 포함된 parameter는 canonical graph에 기존 값이 남아 있어도 configured로 인정하지 않는다. 이 우선순위는 `required_configuration`, `required_any_configuration`과 node mode별 필수 검사에 동일하게 적용한다. Slack payload는 API/Webhook mode 모두 `message|blocks|attachments` 중 하나 이상을 요구하며 공백 문자열, 빈 JSON 배열, invalid JSON과 deferred 값은 payload로 인정하지 않는다. 각 payload task는 개별 optional이지만 세 task를 모두 비운 채 configuration을 완료할 수 없다.
일반 Node Detail에서 deferred parameter를 직접 편집해 기존 값과 다른 유효한 값을 저장하면 client는 그 parameter key만 `_deferred_parameters`에서 제거한다. 다른 parameter 편집, 같은 값의 재전송, 빈 값 또는 invalid 값, viewport/autosync는 marker를 해제하지 않는다. 이 규칙은 최상위 node와 중첩 `subGraph` node에 동일하게 적용하며 Gateway가 저장 시 `configuration_state`를 다시 계산한다. 일반 editor 복구는 Agent Builder의 persisted task status/version이나 decision audit을 변경하지 않는다.
18. Parameter decision은 client-generated `operation_id`와 expected task version을 포함한다. Backend는 parent request row를 잠그고 target task/version과 action별 허용 상태를 확인한 뒤 첫 decision만 처리한다. 새 direct-edit 결과의 안전한 `user_request|existing_graph|upstream_selector|catalog_default` 값은 structural graph save와 acknowledgement가 확인된 뒤 별도 confirm 없이 `completed`로 표시한다. Pending structural group에서는 이 상태를 완료 UI나 다음 task 진행 근거로 사용하지 않는다. 완료 추천값은 접힌 요약에 남고 사용자가 `수정`을 열어 `set`할 수 있다. 기존 session의 active 추천을 위한 `confirm` action은 호환 경로로 유지하며 canonical graph 값과 recommendation context가 일치할 때만 GraphMutation 없이 완료한다. 값 설정 `set`은 `active|completed|skipped|deferred|invalid` task에 허용하며 유효한 값의 acknowledgement가 끝난 뒤에만 `completed`로 전환한다. Catalog validation이 실패한 `set`도 operation id, payload fingerprint와 safe invalid 결과를 기록하며 같은 제출 재시도에는 최초 invalid 결과를 반환하고 audit와 task version을 반복 변경하지 않는다. `pending`은 순차 진행으로 active가 된 뒤 처리하고 `canceled`는 다시 편집하지 않는다. 다른 동시 decision은 `task_conflict`로 거부하며 GraphMutation이나 다음 task를 중복 생성하지 않는다. 기존 `AgentBuilderRequest.response_payload` JSON은 nested object를 제자리 변경하지 않고 전체 새 객체를 재할당해 저장한다.
19. `previous`는 canonical task status/version, workflow graph와 Workflow history를 변경하지 않는 client-only navigation이다. 현재 presentation task가 canonical `active|completed|skipped|deferred`인 경우 backend는 stable order상 이전 재편집 가능 task를 `next_task_id`로 반환하고 frontend는 이를 presentation cursor로 소비해 card, node selection과 focus를 이동한다. `previous`로 이동한 뒤에는 새 card heading으로 접근성 focus를 옮기되 input 값을 자동 변경하지 않는다.
20. ParameterTask를 다시 표시할 때 실제 값은 canonical workflow graph와 Catalog parameter mapping에서 읽어 typed input의 일시적 초기값으로 사용한다. 값은 task/session/audit payload에 복제하지 않는다. LLM `referenced_variables`는 selector 목록과 함께 canonical `name`을 보존해 재저장하므로 기존 `{{변수명}}` prompt가 바뀌지 않는다. `skipped|deferred` task에 graph 값이 없으면 빈 control을 표시한다. Credential/resource reference는 현재 사용자 권한으로 다시 조회 가능한 safe opaque reference만 표시하며, 권한을 잃었거나 삭제된 reference는 ID와 label을 노출하지 않고 사용할 수 없는 기존 설정으로 표시한다. Raw secret, token과 API key는 복원하거나 표시하지 않는다.

완료 상태는 모든 필수 Knowledge 선택과 parameter 확인, 관련 graph 저장과 acknowledgement가 끝난 뒤에만 명시적으로 표시한다. 이 조건을 충족하지 않은 결과에는 완료 history boundary Undo를 허용하지 않는다.

자동 추천값은 원문이 아닌 canonical SHA-256 `recommendation_fingerprint`를 safe task metadata에 남긴다. 이 fingerprint는 structural acknowledgement 후 자동 완료 검증, 기존 session `confirm` 호환과 이후 `set` 충돌 판정에 사용한다. Secret task에는 자동 추천값이나 fingerprint를 만들지 않고 현재 mode에서 필요한 미설정 task를 `active|pending`으로 유지한다.

Agent Builder의 masked secret control은 raw 값을 ParameterDecision이나 GraphMutation으로 보내지 않는다. Frontend editor adapter가 현재 node의 기존 secret 저장 mapping으로 값을 적용하고 일반 draft save를 완료한 뒤, canonical draft metadata 변경을 기준으로 session을 다시 조회해 해당 task의 완료 여부와 다음 task를 동기화한다. 기존 원문은 task/session 또는 input hydration에 복제하지 않는다.

원래 mutation 제출 흐름에서 acknowledgement 응답만 유실되면 client는 같은 `operation_id`와 canonical metadata로 acknowledgement를 정확히 한 번 재시도할 수 있다. 그 재시도 뒤 또는 직접 session 조회, pending request polling, acknowledgement 확인 중 transport 또는 5xx 오류가 발생하면 client는 acknowledgement를 다시 전송하지 않고 같은 session context를 삭제하지 않은 채 `1초 -> 2초 -> 4초` 간격으로 최대 세 번 session 조회만 자동 확인한다. 세 번 모두 결과가 불명확하면 `결과 확인 필요` 상태와 명시적 `다시 확인` control을 표시한다. 성공한 session 응답이 같은 `pending_request`를 반환하면 60초까지 정상 `계획 중` 상태를 유지하면서 5초 간격으로 조회한다. 60초를 넘기면 `평소보다 오래 걸리고 있습니다`를 표시하고 10초 간격으로 처리 제한시간까지 조회한다. Terminal 응답을 받으면 기존 planning 항목을 교체한다. Transport 또는 5xx가 발생하면 자동 조회를 중단하고 `결과 확인 필요`를 표시한다. 사용자가 다시 확인을 선택하면 새 세 번의 session 조회 구간만 시작하며, 자연어 요청, planner, GraphMutation 또는 acknowledgement를 추측하여 재실행하지 않는다. `stale_protocol`, server가 명시한 session not found 또는 invalid session만 local session pointer를 제거하고 새 direct-edit session 전환을 허용한다.

`processing` request의 실행 기한은 session/request 대화 보존 기간과 분리한다. Gateway는 request 생성 후 4분 안에 terminal 상태를 기록하지 못한 `processing` row를 canonical session 조회 또는 다음 요청 admission에서 `failed`로 원자 전환하고 pending gate를 해제한다. 늦게 도착한 planner 결과는 이미 terminal 처리된 request를 덮어쓰거나 GraphMutation을 발급하지 않는다. Client는 이 terminal 응답으로 기존 `planning` 항목을 교체하며 같은 자연어 요청을 자동 재제출하지 않는다.

21. Mail/Gmail처럼 runtime이 관리 credential reference를 요구하고 organization-scoped use 권한 resolver가 존재하는 provider만 `credential_ref` task와 permission-filtered picker를 제공한다. Gmail Draft에는 `provider=gmail`, `auth_type=oauth2`인 use-permitted credential만 후보와 제출 대상으로 허용한다. Slack/GitHub에는 Agent Builder 전용 credential resource나 picker를 만들지 않고, 기존 node 설정과 동일한 Bot Token, API token, webhook URL을 masked `secret` task로 직접 입력한다. 이 runtime 필수 secret task는 `나중에 설정`으로 명시적 defer할 수 있지만 task와 node는 `deferred`/`unresolved`로 남고 test/run/deploy는 계속 차단한다. 기존 원문은 표시하지 않으며 새 입력은 frontend editor adapter의 기존 draft save mapping으로만 전달한다. Agent Builder parameter decision endpoint, GraphMutation/API 응답, task/session, audit, trace와 log에는 raw secret을 포함하지 않는다. 일반 text/JSON/reference control, planner hint와 자연어 message의 secret-like 값도 fail-closed로 거부한다.
22. `direct_edit_v1` Knowledge 후보는 `knowledge_resolution.candidates`와 전용 Knowledge selection endpoint로만 반환·제출한다. Candidate가 비어 있어도 상위 `resolution_id`로 empty selection을 제출한다. Frontend와 selection service는 `clarification_options`를 direct 후보 fallback으로 읽지 않고, 같은 후보를 `clarification_options`에 중복 반환하지 않으며 message endpoint의 legacy `selected_knowledge_candidate(s)` 입력은 거부한다. 같은 resolution이 `pending_ack|completed`이면 legacy/direct 교차 제출이나 중복 operation을 허용하지 않는다. Catalog의 `llmNode.knowledgeBases`는 저장 graph binding의 schema로만 사용하고 direct-edit에서는 일반 `resource_ref` ParameterTask 또는 별도 후보 picker를 만들지 않는다. 이전 direct-edit session에 저장된 같은 generic task는 session 복구 시 제거하고 남은 task를 다시 순차 상태로 정리한다.
23. Knowledge 선택 중에는 하나의 설정 card와 선택값을 유지하고 save/acknowledgement 성공 뒤에만 대화형 선택 결과를 확정한다. 실패는 같은 card에서 재시도할 수 있고 결과가 불명확하면 canonical session의 안전한 `messages`와 `knowledge_resolution`을 다시 hydrate해 `unapplied|pending_ack|completed`를 판정한다. `unapplied`는 같은 card와 선택값으로 재시도하고, `pending_ack`는 control을 잠근 채 reconciliation을 계속하며, `completed`는 선택 card를 닫고 다음 설정 또는 완료 단계로 진행한다. Frontend 실패 경로는 canonical session read를 수행하고, `before_graph` structural operation의 typed payload가 저장 전에 유실되면 server는 연결된 Knowledge resolution을 `unapplied`로 되돌려 같은 card에서 새 operation으로 재시도하게 한다. 자연어 요청이나 planner를 다시 호출하지 않고 응답에서 유실된 typed operations도 재생하지 않는다.
24. 완료 task의 수정은 result group의 명시적 `editing` presentation 상태다. 편집 중에는 완료 표시를 숨기고 active task 유무와 관계없이 취소/닫기를 제공하며 실패 시 입력값을 유지한다. Acknowledgement 뒤에만 편집을 닫고 완료 상태로 돌아간다. 자동 추천 출처는 `user_request=사용자 요청에서 확인`, `existing_graph=기존 Workflow 설정 사용`, `upstream_selector=이전 노드 출력에서 연결`, `catalog_default=기본값 추천`의 safe 문구로 표시한다. `existing_graph`는 Agent Builder 시작 전 canonical base graph에 있던 node의 실제 설정값에만 사용한다. mutation이 추가한 node의 template/default 값은 `catalog_default`, server가 확정한 upstream selector는 `upstream_selector`로 표시한다. Knowledge recommendation reason은 allowlisted 사용자 문구로만 표시하고 알 수 없는 내부 enum은 원문을 노출하지 않는다.
25. Knowledge CTA는 timing을 반영한다. `before_graph`는 `선택한 Knowledge Base로 생성`/`Knowledge Base 없이 생성`, `after_graph`는 `선택 적용`/`Knowledge Base 없이 계속`을 사용한다.
26. 완료 boundary 첫 Undo의 재진입 대상은 status와 최대 `stable_order`만으로 선택한다. `secret_forbidden`, `credential_ref`, provider 또는 node type을 이유로 제외하지 않는다. Raw secret과 권한을 잃은 reference 차단은 graph hydration/rendering 경계가 담당한다. Session reload와 `stale_protocol` 전환은 만료되지 않은 request의 redaction을 통과한 안전한 대화 이력을 시간순으로 복구한다. `stale_protocol`에서는 legacy graph/draft/apply를 폐기하고 안전한 대화만 읽기 전용으로 유지한다.
27. Agent Builder가 `conditionNode` 뒤의 edge를 생성할 때 모든 outgoing edge는 case id 또는 `default`인 명시적 `sourceHandle`을 가져야 한다. 생성기가 만든 단일 선형 downstream edge만 mutation 발급 전에 downstream node를 보존한 채 `default` handle로 명시화하며, handle 없는 edge가 여러 개이거나 이미 explicit default와 충돌하면 target을 추측하지 않고 validation failure로 닫는다. Backend는 동적인 case 목록과 default 각각에 대해 기존 node 또는 `연결 안 함`을 선택하는 typed ParameterTask를 만들고, 기존 explicit edge의 target은 control 초기값으로 hydrate하되 사용자가 branch decision을 확인하기 전에는 Condition configuration을 `unresolved`로 계산한다. `cases` 변경 acknowledgement 뒤에는 canonical graph의 case/default handle과 task를 재조정해 새 handle을 pending으로 추가하고 제거된 handle을 canceled로 보존한다. `연결 안 함`은 명시적으로 확인된 terminal decision이며 해당 handle edge를 만들지 않는다. Validator와 Workflow runtime은 같은 handle 계약을 사용하고 handle 없는 edge를 암묵적 default로 해석하지 않는다.

## Authority And Migration

이 ADR은 MBA-228 Agent Builder direct-edit parameter/Knowledge UX와 history boundary의 Accepted authority다. 생성 mode, 기본값, 빠른 생성 eligibility와 mode 전환은 ADR-0054가 보완해 소유한다. ADR-0046은 GraphMutation/CAS 저장을 구체화하는 supporting authority이며 ADR-0019는 Superseded legacy 기록이다. Preview 결과는 characterization fixture로만 고정하고 direct-edit parity와 필수 integration/E2E를 통과한 뒤 API/UI 분기를 제거한다.

저장 전 권한, stale, validation, audit 정책 자체는 폐기하지 않는다. Frontend는 모든 Agent Builder GraphMutation을 local history transaction으로 적용한 뒤 CAS workflow draft 저장을 완료해야 한다. Backend는 저장된 canonical graph hash와 workflow `updated_at`을 확인한 acknowledgement 이후에만 operation 완료, parameter task 전환 또는 Knowledge binding 확정을 기록한다. Direct-edit graph는 일반 editor save endpoint의 additive mutation context를 사용하며 실행·배포 preflight는 별도로 유지한다.

MBA-228에서는 Agent Builder를 별도 서버로 분리하지 않는다. Gateway 내부에서 application, DB adapter, composition 경계를 분리하고 기존 service는 전환 facade로 유지한다. 별도 서버, 신규 Agent Builder table, 전체 schema 파일 분할은 후속 계획으로 관리한다.

MBA-228은 하나의 기능 PR에서 nullable protocol migration, null/`direct_edit_v1` mixed read, legacy `stale_protocol` 복구와 direct-edit parity 뒤 Preview 제거를 구현하고 contract·migration·integration·E2E test를 제공한다. Alembic single head와 기존 DB upgrade를 확인하며 legacy row를 backfill하거나 additive schema를 downgrade하지 않는다. Frontend와 Gateway가 서로 다른 revision으로 배포되는 동안의 프로토콜 호환성, staged rollout/rollback, creation gate와 immutable image 증거는 별도 배포 ADR과 후속 이슈에서 다룬다.

## Consequences

- backend orchestration은 intent planning, capability resolution, GraphMutation generation, parameter task planning으로 분리된다.
- frontend의 Agent Builder panel은 conversation과 task presentation을 담당하고 graph mutation은 workflow store adapter에 위임한다.
- Node Capability Catalog는 단순 allowlist를 넘어 parameter schema와 input/output 계약의 권위가 된다.
- Undo가 rollback UX를 제공하지만 저장 전 권한과 stale 검사는 GraphMutation 발급 시점, 최초 CAS save와 persisted revert save 경계에서 계속 필요하다.
- 기존 Preview Mode 결과는 characterization fixture로만 사용하고 전용 API와 UI는 direct-edit 저장·복구 검증을 통과한 뒤 제거한다. Preview를 수정·확장하거나 활성 fallback으로 유지하지 않으며 한 session에서 preview 방식과 direct-edit 방식을 혼용하지 않는다.
- parameter 설명 품질은 planner가 담당하지만 값의 유효성이나 실행 가능성은 catalog와 runtime validator가 담당한다.
- Parameter task 상태와 workflow graph 값은 canonical graph hash와 workflow `updated_at` acknowledgement를 기준으로 함께 전진하므로 저장 실패나 새로고침 뒤 서로 다른 완료 상태로 복구되지 않는다.

## Non-Goals

- credential 원문을 Agent Builder가 수집하거나 저장하는 기능
- workflow 생성 중 node 실행 또는 외부 action 실행
- runtime에 없는 node capability 추가
- 모든 node panel을 Agent Builder 전용 UI로 복제
- parameter마다 별도 LLM 호출
- 일반 workflow editor의 기존 권한 모델 변경. 단, unresolved 외부 action의 실행·배포 preflight 차단은 MBA-228 범위다.
- Agent Builder의 독립 서버 또는 독립 데이터베이스 도입
- Agent Builder intent model 표시 순서 변경
- Frontend와 Gateway의 무중단 coordinated rollout, 배포 gate, staged rollback과 image artifact 검증

## 2026-07-14 Correction: LLM Knowledge Selection And Input Continuity

- canonical `generation_mode=guided_generate`의 일반 LLM 생성은 planner가 Knowledge 필요성을 명시하지 않았더라도 `after_graph` / `binding_only` Knowledge 선택 단계를 만든다. 기존 `configure_and_generate` 입력은 같은 mode로 정규화한다. 이는 planner JSON을 재해석하는 규칙이 아니라 LLM node의 선택 가능한 binding을 확인시키는 Catalog 정책이다.
- 사용자는 하나 이상의 권한 있는 Knowledge Base를 고르거나 명시적으로 Knowledge Base 없이 계속할 수 있다. 선택 뒤 planner나 자연어 요청을 다시 실행하지 않는다.
- Knowledge candidate의 인덱싱 준비 상태는 생성 또는 binding 선택을 막지 않는다. 사용 권한과 source lifecycle만 후보 노출 경계이며, 준비되지 않은 binding은 실제 실행과 배포 preflight에서 차단한다.
- Knowledge/Parameter 카드가 열려 있어도 새 자연어 요청 composer는 잠그지 않는다. 네트워크 요청 또는 graph 저장 중인 경우만 제출 control을 잠근다.

## 2026-07-15 Correction: External Connection Guidance And Canonical Hydration

- Decision item 21의 Slack/GitHub `credential_ref` task와 빈 picker/defer presentation은 폐기한다. Mail/Gmail은 node runtime이 관리 credential reference를 요구하므로 기존 organization-scoped, use-permitted reference picker를 유지한다.
- Slack/GitHub는 credential 후보를 만들지 않지만 Bot Token, Incoming Webhook URL과 GitHub API Token은 masked `secret` task로 직접 입력한다. 기존 원문을 조회하거나 hydrate하지 않고 새 입력으로만 교체하며 별도의 managed credential resource도 만들지 않는다.
- 위 masked token 입력창과 현재 active token task의 `나중에 설정` 버튼은 Agent Builder의 필수 제품 경로다. Secret이라는 이유로 task/card를 숨기거나 제거해서는 안 되며, Node Detail 이동 버튼, 외부 설정 안내 또는 관리 credential picker로 대체해서도 안 된다. 이 계약을 바꾸려면 이 ADR을 대체하는 별도 Accepted ADR과 기존 직접 입력 회귀 검증이 필요하다.
- Slack API mode에서는 Bot Token, channel과 payload를, Incoming Webhook mode에서는 Webhook URL과 payload를 Agent Builder task로 제공한다. 전송 방식 변경은 반대 mode의 기존 인증 field와 channel을 canonical node data에서 제거하고 현재 mode의 secret task를 활성화한다. Bot Token, Webhook URL 또는 channel의 `나중에 설정`은 명시적 defer이며 unresolved node 저장은 허용하지만 test/run/deploy는 차단한다.
- Slack의 mode, message, Blocks, Attachments 안내는 Catalog의 한국어 문구를 사용한다. 생성 template이 `{{result}}`와 `referenced_variables`를 연결한 경우 이전 node 출력 사용법을 함께 표시한다. Optional JSON task에서 빈 `적용`은 parse failure가 아니라 명시적 `skip`이다.
- Slack `blocks`와 `attachments`의 durable graph 표현은 runtime 호환 JSON 문자열을 유지한다. Agent Builder가 기존 값을 다시 편집할 때는 이 문자열을 JSON array로 정확히 한 번 파싱해 control을 hydrate하고, 제출된 array를 graph materializer가 정확히 한 번 문자열화한다. 파싱할 수 없거나 array가 아닌 기존 값은 자동 덮어쓰지 않고 unavailable로 표시한다.
- GitHub API Token은 runtime/preflight 필수 masked task이며 기존 원문을 표시하지 않고 새 입력만 받는다. `나중에 설정`은 token 요구사항을 없애는 skip이 아니라 unresolved defer이고, 외부 GitHub 호출 전 test/run/deploy 차단을 유지한다. `comment_pr` action에서는 `comment_body`를 표시하고 필수로 처리하며 `get_pr`에서는 이 task를 표시하거나 요구하지 않는다. Action 또는 Slack mode처럼 task 조건을 제어하는 parameter의 CAS 저장과 acknowledgement가 성공하면 canonical graph로 Catalog task를 다시 계획하고 기존 `node_id + parameter_key` task와 병합한 group을 acknowledgement 응답에 반환한다. Catalog의 공통 `visible_when`/`required_when` 조건을 ParameterTask와 test/deployment preflight가 함께 사용하며 빈 댓글과 미설정 token은 외부 GitHub 호출 전에 차단한다. 이 재계획은 Planner LLM을 호출하거나 acknowledgement audit을 반복하지 않는다.
- Provider 내부 `request_timeout_seconds`는 model provider payload에 포함하지 않되 transport timeout에는 적용한다. Google Gemini client는 호출자가 값을 주지 않은 경우 기존 60초 기본값을 유지하고 Agent Builder intent가 전달한 90초 제한은 실제 HTTP 요청에 적용한다.
- `설정하며 생성`의 affected LLM node는 `model_id`, `output_format`, `system_prompt`, `user_prompt`, `assistant_prompt`, 이전 node 출력 연결인 `referenced_variables`, `citationDisplayMode`, `task_group=model_routing`인 `auto_model_routing`을 기본 설정 ParameterTask로 제공한다. 세 prompt 중 하나 이상은 runtime 실행 필수 조건이지만 각각을 모두 required로 만들지 않는다. `output_format.type=text`에서는 JSON Schema를 숨기고, `json`에서는 선택 입력으로 표시한다. 신규 Agent Builder LLM template의 `citationDisplayMode=detailed`는 수정 가능한 안전 추천으로 표시한다. 필드가 없는 기존 LLM은 legacy `hidden` 의미를 보존하고 Agent Builder가 `detailed`를 자동 주입하지 않는다. Knowledge Collection/KB는 일반 ParameterTask가 아니라 기존 전용 Knowledge 흐름이 계속 소유한다. 안전한 추천값은 최초 structural save/acknowledgement 뒤 완료 요약으로 표시하되, Catalog 기본 추천이 `auto_model_routing=false`이면 미체크 상태의 active 확인 task로 표시한다. `false` 확인은 graph를 다시 저장하지 않고, `true` 변경만 기존 `parameter_update -> CDS CAS save -> acknowledgement` 경계로 graph에 반영한다.
- 라우팅 계약이 안정화될 때까지 `fallback_model_id`, refresh interval, validation budget와 maximum cohort는 Agent Builder ParameterTask로 생성하거나 복구하지 않는다. 기존 canonical graph 값과 runtime 계약은 변경하지 않으며 해당 고급 값은 기존 LLM Routing control이 계속 소유한다. Agent Builder 처리 중 model-routing policy API, refresh, cohort API 또는 workflow 실행은 호출하지 않는다.
- `auto_model_routing` 확인 task와 workflow 결과가 완료된 뒤에만 기존 LLM Routing control로 이동하는 고급 설정 action을 제공한다. 이 action은 화면을 열 뿐 graph mutation, save 또는 policy API를 자동 실행하지 않는다.
- `구조만 생성`은 ParameterTask를 만들지 않으므로 Routing 미설정 LLM에 `Routing 설정으로 이동`을 표시한다. 이 navigation action은 대상 LLM Routing control만 열고 graph를 저장하지 않는다.
- `model_id` 후보는 active organization에서 현재 사용자가 사용할 수 있는 chat model만 제공한다. Fallback 후보 선택과 검증은 Agent Builder가 아닌 기존 LLM Routing control이 담당한다. Runtime policy row는 기존 deployment/runtime bootstrap 경계가 canonical graph 설정으로 생성한다.
- LLM 기본 설정 task는 현재 Agent Builder operation의 `affected_node_ids`에 포함된 LLM에만 생성한다. 신규 생성, 전체 교체 결과, 명시적 수정 target, prompt 또는 Knowledge binding이 직접 변경된 기존 LLM이 대상이며 관계없는 기존 LLM이나 layout-only node에는 복구 task를 추가하지 않는다.
- Direct-edit session read는 affected node의 persisted ParameterGroup을 현재 Catalog와 결정적으로 reconcile한다. 기존 task의 identity, 상태, version과 `stable_order`는 보존하고 신규 Catalog task는 기존 최대 `stable_order` 뒤에 Catalog 순서로 추가한다. Completed group은 신규 또는 새로 필수가 된 task가 canonical graph에서 미설정이고 사용자 입력이 필요할 때만 첫 대상 task를 active로 다시 열며, 이미 설정되거나 숨겨진 신규 task만 있으면 completed를 유지한다. Canceled group은 다시 열지 않는다. 복구 중 planner, Knowledge ranking, GraphMutation, workflow save 또는 acknowledgement를 실행하지 않으며 반복 read는 동일 결과를 반환한다. 확인되지 않은 legacy `auto_model_routing=false` version 1 task에는 기존 1회 보정 규칙을 적용한다.
- Slack의 legacy `body.text|body.channel`은 runtime 전송 payload나 채널이 아니므로 `message|channel` 설정으로 승격하거나 configuration 완료로 판정하지 않는다. 실제 `channel`과 `message|blocks|attachments`가 없으면 test/run/deployment preflight를 fail-closed한다.
- 기존 GitHub graph에 `action` 필드가 없으면 Catalog hydration과 preflight read에서 runtime 기본값과 같은 `get_pr`로 해석한다. 이 호환 read는 graph를 자동 저장하거나 mutation을 발급하지 않으며 명시적인 null 또는 잘못된 action을 기본값으로 바꾸지 않는다.
- `mailAcknowledgeNode` runtime schema는 저장 materializer가 계산한 `configuration_state=resolved|unresolved`만 server-derived field로 허용하고 다른 미정의 필드는 계속 거부한다.
- Canonical graph를 Undo, Redo, acknowledgement 또는 response-loss recovery로 다시 표시할 때 client는 server graph에 없는 editor-only `displayNumber`를 재생성한다. 이 값은 graph hash, CAS payload 또는 server graph에 저장하지 않는다.
- resource/reference task는 candidate id와 server-issued `reference_value`를 모두 사용해 canonical graph의 기존 값을 hydrate한다. 권한 상실 또는 삭제로 어느 후보와도 대응하지 않는 값만 안전한 unavailable state로 표시하고, task를 완료로 추측하지 않는다.

## 2026-07-18 Correction: Direct Knowledge Input Convergence

- `direct_edit_v1` message request의 legacy `selected_knowledge_candidate`와 `selected_knowledge_candidates`는 `HTTP 422`와 공통 machine code `invalid_request`로 거부한다. 사용자 안내는 현재 방식의 전용 Knowledge 선택 화면을 사용하도록 설명한다.
- 활성 `after_graph` Knowledge resolution의 target LLM을 사용자가 기존 Node Detail에서 직접 수정하면, frontend는 이를 별도 로컬 저장으로 확정하지 않고 같은 Agent Builder Knowledge selection endpoint에 전달한다. Server는 target node가 canonical placement와 같은지 확인하고 resource ID를 현재 organization에 발급된 opaque handle로 변환한 뒤 권한, lifecycle, CAS 저장과 acknowledgement를 다시 적용한다.
- Node Detail 동기화는 활성 resolution의 정확한 target에서만 동작한다. 일반 LLM node 설정, 다른 target, `before_graph`, Agent Builder save/acknowledgement 처리 중에는 기존 editor 동작을 가로채지 않거나 안전하게 차단한다.
- 이 경로는 자연어 요청이나 planner를 다시 호출하지 않는다. 성공한 canonical selection은 Agent Builder card와 Node Detail에 같은 상태로 반영한다.

## 2026-07-19 Correction: Secret Input Boundary And Previous-Task Actions

Secret persistence is governed by [ADR-0062](ADR-0062-workflow-node-secret-reference-boundary.md). The masked direct-input controls and `나중에 설정` action below remain mandatory, but any older wording that places plaintext in Workflow node data through the draft save bridge is superseded. Agent Builder submits the new value to the authenticated workflow-node secret boundary and stores only the returned opaque reference in the graph.

- Slack Bot Token, Slack Incoming Webhook URL과 GitHub API Token처럼 Catalog가 `secret`으로 선언한 값은 direct-edit task와 masked password control로 제공한다. 기존 원문은 표시하지 않고 새 입력으로 교체하며, Node Detail 강제 이동 action으로 대체하지 않는다. 일반 Node Detail 진입 기능과 LLM Routing 설정 이동 action 자체는 이 결정의 삭제 대상이 아니다.
- `이전 항목`은 canonical task 상태를 바꾸지 않는 presentation 이동이다. 따라서 이전 task의 control과 decision action은 server의 현재 `active` task ID가 아니라 화면에 표시 중인 presentation task와 canonical graph 값을 기준으로 계산한다.
- 이전에 표시한 optional task의 canonical graph 값이 없으면 `건너뛰기`를 표시하고 기존 `skip` decision을 사용한다. 일반 parameter에 값이 있으면 `값 지우고 건너뛰기`와 `clear -> CAS save -> acknowledgement`를 사용한다. Secret task도 `이전 항목` presentation 대상이 될 수 있지만 기존 원문을 hydrate하지 않고 빈 masked control을 표시한다. Required task와 `confirmation_required=true` task에는 일반 `건너뛰기`와 clear를 표시하지 않는다. 다만 Catalog가 `allow_unresolved`로 선언한 required secret의 현재 active 입력에는 `나중에 설정`을 표시하고 `defer`로 처리한다.
- 이전 task로 이동하는 것만으로 graph 값, task status/version, Workflow history와 다음 active task를 변경하지 않는다. 실패하면 현재 form 값과 presentation 위치를 유지한다.
