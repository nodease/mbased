# 팀별 온보딩 적응형 모델 라우팅 실험 계획

Status: Draft

## 이 실험을 하는 이유

자동 모델 라우팅이 켜져 있다는 화면만으로는 기능이 동작한다고 볼 수 없다. 실제로는
서로 다른 문의가 올바른 입력군으로 분류되고, 새로운 트렌드가 입력군으로 발견되며,
검증을 통과한 모델이 정책에 들어가고, 오래 사라진 트렌드가 휴면으로 바뀌는 전체
흐름을 확인해야 한다.

이 실험은 `팀별 온보딩 문서 접근 제어` workflow를 복제해 **RAG 결과 품질을 유지한
상태에서 입력군과 모델 정책이 시간에 따라 적응하는지** 확인한다.

## 실험 가설

1. 공통, 플랫폼, 영업 문의는 미리 만든 입력군 초안에 매칭된다.
2. 초안에 없는 재무 문의 10개는 두 점검 구간에 걸쳐 반복되므로 자동 입력군 후보가 된다.
3. 영업 문의가 최근 40건에서 5% 이하로 세 번 연속 확인되면 영업 입력군은 휴면이 된다.
4. 마지막 영업 문의 5개로 최근 40건 비중이 10% 이상이 되면 다시 활성화된다.
5. 후보 모델은 모두 바로 정책에 들어가지 않는다. 월 $3 한도 안에서 Replay와 Judge
   품질 gate를 통과한 모델만 해당 입력군 rule에 연결된다.
6. 모델이 바뀌어도 각 답변은 기대한 온보딩 PDF를 근거로 사용한다.

## 실험 환경

| 항목 | 값 |
| --- | --- |
| 계정 | demo seed의 People 팀 manager `jimin.park@nodease.demo` |
| 계정 선택 이유 | 네 개 온보딩 KB를 모두 사용할 수 있어 RAG 권한 차단과 라우팅 오류를 분리해 볼 수 있음 |
| 실행 경로 | 로그인 사용자용 `POST /api/v1/deployments/{id}/run` |
| 기본 모델 | `gpt-5.6-luna` |
| 제외 모델 | `gpt-5.6-sol` |
| 점검 주기 | 배포 후 운영 실행 5회 |
| 검증 예산 | 월 $3 |
| 입력군 한도 | 6개 |
| 최대 provider 호출 상한 | 500회 |
| 최대 시간 | 120분 |

테스트 실행이나 DB insert로 결과를 만들지 않는다. 모든 관찰값은 인증된 배포 실행을
통해 생성하고, 실행 결과와 policy는 공개된 Gateway API로 다시 조회한다.

## 원본과 복제본의 차이

복제본은 원본과 같은 시작 node, LLM prompt, RAG 4종, 검색 threshold/topK,
temperature/max_tokens, answer node와 edge를 사용한다. 다음 두 축만 바꾼다.

1. `auto_model_routing=true`, 입력군 초안 3개, 5회 점검, 월 $3 검증 한도를 추가한다.
2. 기본 모델을 `gpt-5.6-luna`로 설정하고 `gpt-5.6-sol`은 후보에서 제외한다.

따라서 결과가 달라졌다면 원본 workflow 구조가 아니라 자동 라우팅 정책과 모델 선택의
영향을 우선 확인할 수 있다.

## 입력군 초안

| key | 한국어 이름 | 대표 문의 | 고정 |
| --- | --- | --- | --- |
| `common_security` | 공통 계정·보안 온보딩 | 입사 첫날 SSO, MFA, 보안 교육 순서 | 예 |
| `platform_access` | 플랫폼 개발환경·접근 권한 | Git, VPN, 운영 조회 권한 신청 | 아니오 |
| `sales_enablement` | 영업 CRM·고객 데이터 온보딩 | CRM 접근과 고객 데이터 교육 | 아니오 |

공통 입력군은 트래픽이 줄어도 유지해야 하는 안전·기본 안내이므로 고정한다. 플랫폼과
영업 입력군은 실제 트렌드 변화를 검증하기 위해 고정하지 않는다.

## 61개 입력의 시간 순서

| 실행 구간 | 개수 | 문의 구성 | 확인할 변화 |
| --- | ---: | --- | --- |
| 1~6 | 6 | 영업 CRM·견적·고객 데이터 | 영업 입력군 초기 관찰 |
| 7~16 | 10 | 재무 회계·결산·지급 승인 | 새 재무 트렌드 자동 발견 |
| 17~56 | 40 | 회사 공통 20 + 플랫폼 20 | 영업 비중 저하와 휴면 |
| 57~61 | 5 | 영업 CRM·견적·고객 데이터 | 영업 입력군 재활성화 |

각 구간 내부 순서는 seed `270`으로 재현 가능하게 섞는다. 구간 순서는 lifecycle을
의도대로 검증해야 하므로 섞지 않는다. 질문 문장은 서로 다르며 실험 보고서에 실제
순서와 기대 근거를 모두 기록한다.

## RAG 기대값

| 문의 종류 | 기대 문서 | 근거가 되는 내용 |
| --- | --- | --- |
| 공통 | `company_common_onboarding.pdf` | 첫날 일정, SSO/MFA, 보안 교육, 메신저, 완료 기준 |
| 플랫폼 | `platform_team_onboarding_v4.pdf` | Git, VPN, 개발환경, 운영 조회, 배포 권한 |
| 영업 | `sales_team_onboarding_v2.pdf` | CRM, 고객 배정, 견적 승인, 고객 데이터 취급 |
| 재무 | `finance_team_onboarding_v3.pdf` | 회계 시스템, 결산, 지급 승인, 업무 분리 |

답변 원문을 자동 정답으로 판정하지 않는다. 먼저 기대 문서가 검색 근거에 포함됐는지,
workflow와 LLM node가 성공했는지, schema와 후속 node가 통과했는지를 확인한다. 모델
후보의 최종 품질은 별도 Replay/Judge gate가 판정한다.

## 모델 검증 흐름

1. 기본 정책은 Luna를 사용한다.
2. 각 입력군에 운영 관찰이 쌓이면 현재 credential로 호출 가능한 후보만 남긴다.
3. 제외 목록의 Sol은 후보에서 제거한다.
4. 후보별 대표 입력 두 개를 Replay하고 Judge 품질, schema, downstream, fallback을 본다.
5. 월 $3 안에서 품질 gate를 통과한 후보만 입력군 rule에 연결한다.
6. 검증 후보가 없거나 품질이 부족하면 Luna를 유지한다.

따라서 “모델이 바뀌지 않았다”는 결과가 항상 버그는 아니다. 검증 batch가 생성됐는지,
후보가 사용 가능했는지, 예산이 남았는지, 품질 gate가 왜 통과하지 못했는지를 함께
봐야 한다.

### 실제 정책 변화

1. 1~6회에는 저장 모델인 `gpt-5.6-luna`를 사용하면서 초안 입력군을 DB row로
   승격하고 운영 관찰을 모았다.
2. 7~16회의 재무 문의가 기존 입력군에 충분히 가깝지 않은 반복 trend로 쌓였다.
   서버는 이를 자동 입력군으로 만들고 10개 Replay 항목을 검증했다.
3. 검증을 통과한 재무 입력군은 `gpt-4o-mini`와 `gpt-4.1-mini` evidence를 얻었다.
   이후 재무 문의 17~18회는 더 저렴한 `gpt-4o-mini`로 실제 실행됐다.
4. 공통·플랫폼 문의가 이어진 뒤 플랫폼 관련 자동 입력군이 하나 더 발견됐다.
   두 번째 Replay에서는 `gpt-4.1-mini`가 통과하고 `gpt-4o-mini`는 탈락했다.
   플랫폼 문의 54회는 `gpt-4.1-mini`로 실행됐다.
5. 영업 초안 입력군은 최근 traffic 비중이 낮아져 휴면이 됐다. 마지막 5개 영업
   문의는 재활성화 기준을 만족시키기에 관찰 수와 점검 구간이 부족했다. 따라서
   재활성화가 실패한 것이 아니라 이번 61회 범위에서는 아직 확인되지 않은 상태다.

### 초안 입력군이 바로 선택되지 않은 이유

초안 입력군은 사용자 의도를 먼저 저장하기 위한 설정이다. 초안 대표 문의 하나와 실제
문의 표현이 충분히 가깝지 않으면 runtime이 억지로 같은 입력군으로 분류하지 않는다.
이번 실험의 manual 입력군 3개도 DB 승격에는 성공했지만 대부분의 실제 문장과 0.60
기준을 넘지 못해 즉시 active rule이 되지 않았다. 대신 반복된 재무·플랫폼 표현은
운영 관찰에서 별도 자동 입력군으로 발견됐다.

이 결과는 초안 기능이 불필요하다는 뜻이 아니다. 초안은 고정해야 할 업무 영역과
사용자 이름을 미리 보존하고, 실제 활성 rule은 운영 증거와 유료 검증을 통과한 뒤에만
생기도록 안전 경계를 제공한다. 초안의 초기 매칭률을 높이려면 대표 문의를 한 문장만
쓰는 대신 서로 다른 표현의 합성 예문을 여러 개 만들거나, 입력군 마법사가 예문을
확장하는 후속 보완이 필요하다.

### 남은 제품 보완점

- 휴면 입력군 재활성화는 5건만으로 단정하지 말고 추가 영업 입력과 다음 정책 점검
  구간까지 실행해 확인해야 한다.
- RAG 기대 출처가 빠진 3건은 답변 실패로 단정할 수 없다. 검색 결과의 파일명 trace가
  누락됐는지, 검색이 다른 문서를 선택했는지 각각 확인해야 한다.
- 자동 발견 입력군의 화면 label이 `자동 발견 입력군 4`처럼 보인다. 실제 문의 trend를
  설명하는 사용자 친화 이름을 안전한 합성 요약으로 생성하는 작업이 필요하다.
- 실험 중 provider가 한 차례 불완전 응답을 반환했다. 제품은 부분 출력을 성공으로
  처리하지 않았고 재시도했지만, 원격 재현 스크립트는 한 요청의 외부 장애 때문에
  전체 실험이 중단되지 않도록 실패 요약과 checkpoint를 남긴다.

상세 실행 순서와 각 run의 safe metadata는
`reports/model-routing/history/team-onboarding/local-20260715-final-v5/report.md`에서 확인한다.

## 실험 후 결론 작성 규칙

실험 전 가설을 실제 결과처럼 쓰지 않는다. 결과 보고서는 다음을 분리한다.

- 실제 확인: run id와 trace로 증명된 사실
- 부분 확인: 일부 실행에서만 확인되거나 trace 정보가 부족한 사실
- 실패: 기대와 달랐고 재현된 사실
- 미검증: provider 권한, 예산, 시간 제한 때문에 실행하지 못한 사실

실제 결과는
`reports/model-routing/history/team-onboarding/<run-name>/report.md`에 생성한다.
