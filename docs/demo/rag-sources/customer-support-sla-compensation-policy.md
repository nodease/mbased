# 고객지원 SLA 위반 가능성 및 보상안 운영 정책

문서 상태: 내부 운영 기준  
문서 소유 부서: 고객지원 운영팀, 고객성공팀, 서비스 신뢰성팀  
적용 범위: Nodease Enterprise 고객지원 티켓, 장애 문의, 계약 SLA 문의, 보상 요청  
보안 등급: 사내 공개  
최종 개정: 2026. 7. 7.

## 1. 목적

이 문서는 고객지원 티켓을 처리하는 담당자와 AI 지원 워크플로우가 고객 문의의 긴급도를 판단하고, SLA 위반 가능성을 분류하며, 계약과 정책에 맞는 답변 초안을 작성하기 위해 사용한다.

본 문서는 다음 질문에 답하기 위한 기준을 제공한다.

- 고객 문의가 긴급 티켓인지 아닌지 판단하는 기준
- SLA 위반 가능성이 있는지 판단하는 기준
- SLA 위반 또는 위반 우려 상황에서 제공 가능한 보상안
- 보상안 안내 시 고객에게 말해도 되는 내용과 말하면 안 되는 내용
- 티켓 답변 초안에 반드시 포함해야 하는 항목
- 내부 에스컬레이션이 필요한 조건

AI 워크플로우는 이 문서를 근거로 고객지원 티켓을 분류할 수 있다. 단, AI가 보상 지급을 최종 승인해서는 안 된다. 보상 지급 확정, 계약 해석, 금액 산정, 법적 책임 인정은 고객성공 매니저 또는 계약 담당자의 승인 이후에만 가능하다.

## 2. 핵심 용어

### SLA

SLA는 Service Level Agreement의 약자이며, 고객과 회사가 계약상 합의한 서비스 가용성, 응답 시간, 복구 시간, 지원 채널, 보상 조건을 의미한다.

### SLA 위반

SLA 위반은 계약서 또는 주문서에 명시된 가용성, 초기 응답 시간, 복구 시간, 처리 기한, 지원 등급 약속을 충족하지 못한 상태를 의미한다.

SLA 위반은 단순 불만과 다르다. 고객이 불편을 겪었더라도 계약 기준을 벗어나지 않았다면 SLA 위반으로 확정하지 않는다.

### SLA 위반 가능성

SLA 위반 가능성은 아직 최종 판정 전이지만, 고객 문의 내용이나 시스템 로그상 SLA 위반으로 이어질 수 있는 징후가 있는 상태를 의미한다.

예를 들어 다음 상황은 SLA 위반 가능성으로 본다.

- 고객이 유료 Enterprise 플랜이며, 서비스 중단 시간이 계약 기준에 근접하고 있음
- 장애가 계속 진행 중이고 복구 예정 시간이 명확하지 않음
- P1 또는 P2 티켓인데 초기 응답 시간이 내부 목표를 초과했거나 초과 직전임
- 고객이 명시적으로 "SLA", "보상", "크레딧", "계약 위반", "환불"을 언급함
- 동일 장애에 대해 다수 고객이 반복 문의함

### 서비스 크레딧

서비스 크레딧은 현금 환불이 아니라 다음 청구 기간에 사용료에서 차감되는 계약상 보상 수단이다. 별도 계약이 없는 경우 현금 지급 대신 서비스 크레딧을 기본 보상 수단으로 한다.

### 가용성

가용성은 고객이 정상적으로 제품 기능을 사용할 수 있었던 시간을 의미한다. 고객의 자체 네트워크, 브라우저 확장, 잘못된 API 호출, 권한 설정 오류, 고객사 내부 방화벽으로 인한 장애는 회사 서비스 가용성 계산에서 제외될 수 있다.

### 초기 응답 시간

초기 응답 시간은 티켓이 정상 접수된 시점부터 고객에게 첫 의미 있는 응답을 제공하기까지 걸린 시간이다. 자동 접수 확인 메시지는 초기 응답으로 보지 않는다. 사람이 확인했거나 AI가 정책에 맞는 초기 안내를 제공하고 담당 큐로 연결한 경우에만 초기 응답으로 본다.

## 3. 지원 플랜과 SLA 기준

Nodease 고객지원 SLA는 고객 플랜에 따라 다르다. 티켓 분류 시 고객 플랜을 먼저 확인해야 한다.

### 3.1 Free 플랜

Free 플랜은 공식 SLA를 제공하지 않는다.

- 지원 채널: 커뮤니티, 문서, 제한적 이메일
- 초기 응답 목표: 영업일 기준 3일 이내
- 보상: 제공하지 않음
- 긴급도 true 판단: 원칙적으로 false

단, Free 플랜이라도 보안 취약점 제보, 개인정보 노출 가능성, 광범위한 서비스 장애를 제보하는 경우 긴급도 true가 될 수 있다.

### 3.2 Starter 플랜

Starter 플랜은 제한적 지원 목표를 제공하지만 계약상 보상 SLA는 제공하지 않는다.

- 지원 채널: 이메일, 웹 티켓
- 초기 응답 목표: 영업일 기준 1일 이내
- 복구 목표: 별도 보장 없음
- 월간 가용성 목표: 99.0%
- 보상: 원칙적으로 제공하지 않음
- 긴급도 true 판단: 서비스 전체 이용 불가, 결제 장애, 데이터 접근 불가, 보안 이슈일 때 true

Starter 고객에게는 SLA 보상이라는 표현을 쓰지 않는다. "지원 목표", "우선 확인", "처리 상황 공유"라는 표현을 사용한다.

### 3.3 Business 플랜

Business 플랜은 제한적 SLA를 제공한다.

- 지원 채널: 이메일, 웹 티켓, 업무시간 채팅
- 초기 응답 목표:
  - P1: 1시간 이내
  - P2: 4시간 이내
  - P3: 영업일 기준 1일 이내
  - P4: 영업일 기준 3일 이내
- 월간 가용성 목표: 99.5%
- 보상: 월 이용료 기준 최대 10% 서비스 크레딧
- 긴급도 true 판단: P1 또는 P2 조건이면 true

Business 고객의 보상은 고객이 요청하고 내부 검토가 완료된 경우에만 안내한다.

### 3.4 Enterprise 플랜

Enterprise 플랜은 계약 SLA를 제공한다.

- 지원 채널: 전용 티켓 포털, 이메일, 전담 고객성공 매니저, 긴급 연락 채널
- 초기 응답 목표:
  - P1: 15분 이내
  - P2: 1시간 이내
  - P3: 8영업시간 이내
  - P4: 영업일 기준 2일 이내
- 월간 가용성 목표: 99.9%
- 보상: 월 이용료 기준 최대 25% 서비스 크레딧
- 긴급도 true 판단: P1, P2, SLA 보상 언급, 보안/권한/데이터 손실 가능성, 다수 사용자 영향 시 true

Enterprise 고객의 티켓은 계약 번호, 조직 ID, 워크플로우 ID, 영향 범위, 최초 발생 시각을 확인해야 한다.

## 4. 티켓 심각도 분류 기준

AI는 고객 문의 내용을 읽고 심각도를 추정할 수 있다. 다만 최종 심각도는 담당자가 확정한다.

### 4.1 P1 Critical

P1은 고객의 핵심 업무가 중단되었고 우회 방법이 없으며 다수 사용자 또는 프로덕션 시스템에 직접적인 영향을 주는 상황이다.

다음 조건 중 하나라도 해당하면 P1 가능성이 높다.

- 전체 서비스 로그인 불가
- 모든 워크플로우 실행 실패
- 프로덕션 API가 지속적으로 5xx를 반환
- 고객 데이터가 손실되었거나 손실 가능성이 높음
- 권한 오류로 민감 데이터가 잘못 노출됨
- Enterprise 고객의 핵심 업무 자동화가 멈춤
- 장애가 30분 이상 지속되고 복구 예정 시간이 불명확함
- 고객이 "전사 업무 중단", "운영 중단", "매출 손실", "SLA 위반", "계약 위반"을 언급함

P1 티켓은 긴급도 true로 분류한다.

P1 답변 초안에는 다음 내용을 포함해야 한다.

- 장애 또는 문의를 최우선으로 확인 중이라는 안내
- 영향 범위와 발생 시각 확인 요청
- 담당 팀에 즉시 에스컬레이션했다는 안내
- 보상 가능성은 "검토 대상"으로만 표현
- 확정되지 않은 원인이나 보상 금액을 단정하지 않음

### 4.2 P2 High

P2는 주요 기능이 비정상이나 일부 우회 방법이 있고, 특정 팀 또는 일부 워크플로우에 큰 영향을 주는 상황이다.

다음 조건 중 하나라도 해당하면 P2 가능성이 높다.

- 특정 워크플로우 또는 모듈이 반복 실패
- RAG 검색 결과가 지속적으로 비어 있음
- LLM credential 오류로 운영 워크플로우가 실행되지 않음
- 배포된 webhook이 간헐적으로 실패
- 관리자 화면에서 권한 변경이 반영되지 않음
- 고객지원, 결제, 승인 등 업무 중요도가 높은 프로세스가 지연됨
- Business 또는 Enterprise 고객이 업무 영향이 크다고 언급함
- 초기 응답 목표를 초과할 가능성이 있음

P2 티켓은 보통 긴급도 true로 분류한다. 단, 고객 영향이 매우 제한적이고 우회 방법이 명확하면 false가 될 수 있다.

### 4.3 P3 Normal

P3는 기능 사용에 불편이 있으나 핵심 업무 중단은 아니며, 우회 방법이 있거나 단일 사용자에게 제한된 문제다.

예시는 다음과 같다.

- 화면 표시 오류
- 특정 브라우저에서만 재현되는 UI 문제
- 문서 처리 지연
- 일부 설정 저장 실패
- 사용법 문의
- 권한 요청 진행 상태 문의
- 비용 리포트 수치 해석 문의

P3는 일반적으로 긴급도 false로 분류한다.

### 4.4 P4 Low

P4는 제품 개선 요청, 일반 문의, 문서 요청, 기능 제안, 낮은 우선순위의 설정 문의다.

예시는 다음과 같다.

- 새 기능 제안
- 가격 정책 문의
- 사용 사례 상담
- 문서 위치 문의
- UI 문구 개선 요청
- 교육 자료 요청

P4는 긴급도 false로 분류한다.

## 5. 긴급도 true/false 판단 기준

AI가 반환하는 `urgent` 값은 고객지원팀이 즉시 확인해야 하는지 여부를 나타낸다.

### 5.1 긴급도 true로 판단해야 하는 경우

다음 중 하나라도 해당하면 `urgent`를 true로 둔다.

- 서비스 전체 또는 핵심 기능이 작동하지 않음
- 고객의 프로덕션 업무가 중단됨
- 데이터 손실, 데이터 유출, 권한 오작동 가능성이 있음
- Enterprise 고객이 SLA, 계약 위반, 보상, 환불, 크레딧을 언급함
- P1 또는 P2로 볼 수 있는 장애
- 장애가 반복 발생하고 고객이 업무 영향 또는 금전 손실을 언급함
- API, webhook, workflow execution이 대량 실패하고 있음
- 고객이 "지금 바로", "긴급", "업무 중단", "전체 장애", "장애 보상"을 언급함
- 동일 현상에 대해 여러 사용자가 동시에 문의함
- 결제 또는 청구 오류로 고객 서비스 이용이 차단됨

### 5.2 긴급도 false로 판단해야 하는 경우

다음에 해당하면 일반적으로 `urgent`를 false로 둔다.

- 사용법 문의
- 기능 설정 방법 문의
- 가격 정책 문의
- 단일 사용자의 화면 표시 문제
- 우회 방법이 있고 업무 중단이 아닌 문제
- 제품 개선 요청
- 문서 요청
- 계약상 SLA나 보상과 무관한 일반 문의
- 장애가 아니라 예상 동작에 대한 확인 요청

### 5.3 애매한 경우의 원칙

고객 플랜, 영향 범위, 발생 시간이 불명확하지만 SLA 위반 가능성이 조금이라도 있으면 다음 원칙을 따른다.

- Enterprise 고객이면 true에 가깝게 판단한다.
- Business 고객이고 업무 영향이 명확하면 true에 가깝게 판단한다.
- Starter 또는 Free 고객이고 단순 문의면 false로 판단한다.
- 고객이 보상, SLA, 계약 위반을 직접 언급하면 true로 판단한다.
- 고객이 "전체", "프로덕션", "결제", "데이터", "권한"을 언급하면 true로 판단한다.

## 6. SLA 위반 가능성 판단 기준

AI는 티켓 답변 초안에 SLA 위반을 확정적으로 인정해서는 안 된다. 대신 다음 표현을 사용한다.

- "SLA 영향 여부를 확인하겠습니다."
- "계약 기준에 따른 보상 가능성은 내부 검토 후 안내드리겠습니다."
- "현재 정보만으로는 SLA 위반 여부를 확정하기 어렵습니다."
- "장애 시간과 영향 범위를 기준으로 검토하겠습니다."

### 6.1 SLA 위반 가능성이 높은 경우

다음 조건이 있으면 SLA 위반 가능성이 높다.

- Enterprise 고객의 P1 장애가 15분 이상 응답 없이 지속됨
- Enterprise 고객의 P2 장애가 1시간 이상 응답 없이 지속됨
- Business 고객의 P1 장애가 1시간 이상 응답 없이 지속됨
- 월간 가용성이 계약 기준 아래로 떨어질 가능성이 있음
- 배포된 프로덕션 workflow가 장시간 실행되지 않음
- 고객이 업무 중단과 금전 손실을 함께 언급함
- 회사 상태 페이지 또는 내부 모니터링에서 장애가 확인됨
- 같은 시간대에 동일 증상이 다수 조직에서 발생함

### 6.2 SLA 위반 가능성이 낮은 경우

다음 조건이면 SLA 위반 가능성은 낮다.

- 고객 환경 문제로 확인됨
- 고객이 잘못된 API key, 만료된 credential, 잘못된 webhook URL을 사용함
- 고객이 권한이 없는 리소스에 접근하려고 함
- 서비스는 정상이나 고객의 설정이 누락됨
- Free 또는 Starter 플랜의 일반 문의
- 장애 시간이 계약 기준에 미달함
- 고객이 보상 요청을 했지만 실제 장애 근거가 없음

### 6.3 SLA 위반 검토에 필요한 정보

티켓에 다음 정보가 없으면 답변 초안에서 추가 확인을 요청한다.

- 조직명 또는 organization ID
- 고객 플랜
- 발생 시각과 종료 시각
- 영향받은 사용자 수
- 영향받은 workflow ID 또는 app ID
- 오류 메시지 또는 request ID
- 재현 방법
- 비즈니스 영향
- 우회 방법 존재 여부

## 7. 보상안 정책

보상안은 고객 플랜, 계약 조건, 장애 시간, 영향 범위, 고객 귀책 여부에 따라 달라진다.

AI는 보상 금액 또는 크레딧 비율을 확정해서 안내하지 않는다. AI는 가능한 보상 유형과 검토 절차만 안내한다.

### 7.1 기본 보상 유형

#### 서비스 크레딧

서비스 크레딧은 가장 일반적인 SLA 보상이다.

적용 가능 조건:

- Business 또는 Enterprise 고객
- 회사 책임의 서비스 장애
- 계약상 SLA 기준 미달 가능성
- 고객이 정해진 기간 안에 보상 검토를 요청함

안내 예시:

"해당 건은 SLA 영향 여부를 검토할 수 있는 사안입니다. 장애 시간과 영향 범위를 확인한 뒤 계약 조건에 따라 서비스 크레딧 적용 가능성을 검토하겠습니다."

#### 청구 조정

청구 조정은 서비스 크레딧으로 처리하기 어려운 예외 상황에서 사용한다.

적용 가능 조건:

- 중복 청구
- 잘못된 플랜 적용
- 회사 실수로 인한 과금
- 계약서상 별도 조항 존재

안내 예시:

"청구 조정 가능 여부는 계약 및 청구 내역 확인이 필요합니다. 관련 내역을 확인한 뒤 담당자가 안내드리겠습니다."

#### 지원 우선순위 상향

지원 우선순위 상향은 보상보다 빠른 복구가 중요한 상황에 적용한다.

적용 가능 조건:

- 장애가 진행 중임
- 고객 업무 영향이 큼
- 보상보다 해결이 우선임
- 기술 담당자의 실시간 확인이 필요함

안내 예시:

"현재 업무 영향이 큰 상황으로 판단되어 우선순위를 상향해 담당 팀에 전달하겠습니다."

#### RCA 보고서

RCA는 Root Cause Analysis의 약자이며, 장애 원인 분석 보고서를 의미한다.

적용 가능 조건:

- Enterprise 고객
- P1 또는 장시간 P2 장애
- 고객이 내부 보고 또는 감사 목적으로 요청함
- 동일 장애 재발 방지 설명이 필요함

안내 예시:

"장애 원인과 재발 방지 조치가 정리되는 대로 RCA 제공 가능 여부를 함께 검토하겠습니다."

### 7.2 보상 불가 또는 제한 조건

다음 상황은 보상이 제한되거나 제공되지 않을 수 있다.

- 고객사 네트워크, VPN, 방화벽, 프록시 문제
- 고객이 잘못 설정한 API key, webhook, credential 문제
- 고객이 권한 없는 리소스에 접근하려 한 경우
- 고객이 이용 한도, rate limit, 예산 제한을 직접 설정한 경우
- 사전 공지된 정기 점검
- 베타 기능 또는 실험 기능
- Free 플랜
- 계약상 보상 조항이 없는 플랜
- 고객이 장애 발생 후 보상 요청 기간을 넘긴 경우

답변 초안에서는 보상 불가를 단정하지 말고 다음처럼 표현한다.

"현재 정보만으로 보상 가능 여부를 확정하기는 어렵습니다. 원인과 영향 범위를 확인한 뒤 계약 조건에 따라 안내드리겠습니다."

## 8. 보상 비율 참고 기준

다음 기준은 내부 참고용이며 고객에게 확정값으로 안내하지 않는다.

### 8.1 Business 플랜

월간 가용성 99.5% 미만 99.0% 이상:

- 서비스 크레딧 검토 가능
- 일반적으로 월 이용료의 최대 5% 범위

월간 가용성 99.0% 미만:

- 서비스 크레딧 검토 가능
- 일반적으로 월 이용료의 최대 10% 범위

초기 응답 SLA 위반:

- 반복 위반 또는 중대한 업무 영향이 있을 때 고객성공팀 검토
- 자동 보상 대상은 아님

### 8.2 Enterprise 플랜

월간 가용성 99.9% 미만 99.5% 이상:

- 서비스 크레딧 검토 가능
- 일반적으로 월 이용료의 최대 10% 범위

월간 가용성 99.5% 미만 99.0% 이상:

- 서비스 크레딧 검토 가능
- 일반적으로 월 이용료의 최대 15% 범위

월간 가용성 99.0% 미만:

- 서비스 크레딧 검토 가능
- 일반적으로 월 이용료의 최대 25% 범위

P1 초기 응답 목표 중대한 위반:

- 고객성공 매니저 검토 필요
- 반복 발생 시 RCA 제공 권장
- 서비스 크레딧과 별도로 운영 개선 계획 제공 가능

## 9. 답변 초안 작성 원칙

AI가 생성하는 답변 초안은 고객에게 바로 보낼 수 있는 수준이어야 하지만, 확정되지 않은 사실을 단정하지 않아야 한다.

### 9.1 반드시 포함할 내용

긴급 티켓 답변 초안에는 다음 내용을 포함한다.

- 고객 불편에 대한 인정
- 현재 확인 중인 내용
- 추가로 필요한 정보
- 에스컬레이션 또는 우선순위 상향 안내
- SLA 또는 보상은 검토 후 안내한다는 문구
- 다음 업데이트 예정 시간

일반 티켓 답변 초안에는 다음 내용을 포함한다.

- 문의 내용 요약
- 확인 또는 조치 방법
- 필요한 추가 정보
- 예상 처리 흐름

### 9.2 사용해도 되는 표현

- "확인 후 안내드리겠습니다."
- "영향 범위를 기준으로 검토하겠습니다."
- "계약 조건에 따른 보상 가능성은 담당 팀에서 확인하겠습니다."
- "현재 정보만으로는 확정하기 어렵습니다."
- "우선순위를 상향해 확인하겠습니다."
- "장애 시간과 request ID를 공유해 주시면 더 정확히 확인할 수 있습니다."

### 9.3 사용하면 안 되는 표현

- "SLA를 위반했습니다."
- "반드시 보상해 드리겠습니다."
- "월 이용료의 25%를 지급하겠습니다."
- "회사 책임입니다."
- "고객 책임입니다."
- "법적으로 문제가 없습니다."
- "환불은 불가능합니다."
- "이건 긴급하지 않습니다."

위 표현은 법무, 계약, 고객성공, 장애 지휘 담당자의 검토 없이 사용하지 않는다.

## 10. JSON 분류 출력 기준

AI 워크플로우가 티켓을 분류할 때는 다음 JSON 형식을 사용한다.

```json
{
  "urgent": true,
  "draft_reply": "고객에게 보낼 답변 초안"
}
```

필요하면 내부용으로 다음 필드를 추가할 수 있다.

```json
{
  "urgent": true,
  "severity": "P1",
  "sla_risk": "high",
  "compensation_review_required": true,
  "draft_reply": "고객에게 보낼 답변 초안"
}
```

데모 워크플로우가 두 필드만 요구한다면 반드시 `urgent`와 `draft_reply`만 반환한다.

### 10.1 urgent 값

`urgent`는 boolean 값이다.

- 긴급이면 true
- 일반이면 false

문자열 `"true"` 또는 `"false"`를 쓰지 않는다.

### 10.2 draft_reply 값

`draft_reply`는 한국어 문장으로 작성한다.

답변 초안은 고객에게 직접 보낼 수 있는 톤이어야 한다. 내부 용어만 나열하지 않는다.

## 11. 예시 티켓과 분류

### 예시 1. Enterprise API 전체 장애

고객 문의:

"Enterprise 계약 고객입니다. 오늘 10시 15분부터 모든 workflow API가 500을 반환하고 있습니다. 고객 주문 처리 자동화가 멈췄고 SLA 위반이면 보상도 확인해 주세요."

분류:

```json
{
  "urgent": true,
  "draft_reply": "문의 주신 내용은 프로덕션 workflow API 장애와 SLA 영향 가능성이 함께 있는 건으로 우선순위를 상향해 확인하겠습니다. 발생 시각, 영향받은 workflow ID, 대표 request ID를 공유해 주시면 장애 시간과 영향 범위를 기준으로 계약 조건에 따른 보상 검토 가능 여부까지 확인해 안내드리겠습니다."
}
```

판단 근거:

- Enterprise 고객
- 전체 workflow API 실패
- 업무 중단
- SLA와 보상 언급
- 긴급도 true

### 예시 2. Business 고객의 webhook 간헐 실패

고객 문의:

"어제부터 고객 티켓 처리 webhook이 간헐적으로 실패합니다. 전체 장애는 아니지만 몇 건이 누락되어 고객 응대가 지연됐습니다."

분류:

```json
{
  "urgent": true,
  "draft_reply": "고객 응대 지연이 발생한 운영 workflow 문제로 보여 우선 확인하겠습니다. 실패한 webhook 호출 시각, workflow ID, 오류 응답 또는 request ID를 알려주시면 실패 패턴과 영향 범위를 확인해 처리 방향을 안내드리겠습니다."
}
```

판단 근거:

- 운영 workflow 영향
- 고객 응대 지연
- 간헐적이지만 업무 영향 존재
- P2 가능성

### 예시 3. 사용법 문의

고객 문의:

"RAG 문서를 업로드할 때 chunk size는 어느 정도로 설정하면 좋나요?"

분류:

```json
{
  "urgent": false,
  "draft_reply": "일반적인 문서 검색용 RAG 구성에서는 문서 성격에 따라 chunk size를 조정하는 것이 좋습니다. 정책 문서나 매뉴얼처럼 문단 단위 의미가 중요한 문서는 800~1200자 범위에서 시작하고, 검색 결과가 너무 길거나 짧으면 overlap과 함께 조정해 보시는 것을 권장드립니다."
}
```

판단 근거:

- 사용법 문의
- 장애 아님
- SLA와 무관
- 긴급도 false

### 예시 4. 권한 오류와 민감 데이터 가능성

고객 문의:

"일반 멤버 계정에서 관리자용 감사 로그 일부가 보이는 것 같습니다. 실제로 권한이 잘못 열린 건지 확인해 주세요."

분류:

```json
{
  "urgent": true,
  "draft_reply": "권한 범위와 민감 로그 노출 가능성이 있는 문의로 판단되어 즉시 우선 확인하겠습니다. 확인하신 계정, 조직 ID, 접근한 화면 또는 API, 발생 시각, 화면 캡처나 request ID를 공유해 주시면 권한 정책과 감사 로그를 기준으로 영향 범위를 확인하겠습니다."
}
```

판단 근거:

- 권한 오작동 가능성
- 민감 데이터 노출 가능성
- 긴급도 true

### 예시 5. 보상 요청만 있고 장애 근거 부족

고객 문의:

"지난달 서비스가 느렸던 것 같은데 보상 받을 수 있나요?"

분류:

```json
{
  "urgent": false,
  "draft_reply": "보상 가능 여부는 계약 조건과 실제 장애 시간, 영향 범위 확인이 필요합니다. 불편을 겪으신 날짜와 시간대, 사용하신 기능, 오류 메시지 또는 request ID가 있다면 공유해 주세요. 확인 가능한 정보를 기준으로 SLA 영향 여부를 검토하겠습니다."
}
```

판단 근거:

- 구체적 장애 정보 없음
- 즉시 장애 진행 중 아님
- 보상 언급은 있으나 긴급 장애로 보기 어려움
- 긴급도 false

### 예시 6. 고객사 설정 오류

고객 문의:

"API 호출이 모두 실패합니다. 확인해 보니 저희가 예전 API key를 쓰고 있을 수도 있습니다."

분류:

```json
{
  "urgent": false,
  "draft_reply": "API key 설정 문제 가능성이 있어 보입니다. 먼저 현재 사용 중인 credential이 활성 상태인지, 올바른 조직과 workflow에 연결되어 있는지 확인해 주세요. 계속 실패한다면 오류 응답 코드와 request ID를 공유해 주시면 추가로 확인하겠습니다."
}
```

판단 근거:

- 고객 설정 오류 가능성
- SLA 보상 가능성 낮음
- 긴급도 false

### 예시 7. 결제 장애로 서비스 차단

고객 문의:

"카드 결제가 정상 처리됐는데 계정이 결제 실패 상태로 바뀌어 모든 workflow가 정지됐습니다. 오늘 운영해야 하는 자동화가 멈췄습니다."

분류:

```json
{
  "urgent": true,
  "draft_reply": "결제 상태 오류로 운영 workflow가 정지된 상황으로 보여 우선순위를 상향해 확인하겠습니다. 조직 ID, 결제 시각, 결제 영수증 또는 청구서 번호, 정지된 workflow ID를 공유해 주시면 결제 상태와 서비스 제한 여부를 함께 확인하겠습니다."
}
```

판단 근거:

- 결제 오류
- 운영 workflow 정지
- 업무 영향
- 긴급도 true

## 12. 에스컬레이션 기준

AI는 다음 상황을 감지하면 답변 초안에 "담당 팀에 전달" 또는 "우선순위 상향" 표현을 포함한다.

- P1 가능성
- P2 가능성
- SLA 또는 보상 언급
- 보안 또는 권한 문제
- 데이터 손실 또는 데이터 노출 가능성
- 결제 오류로 서비스 이용 차단
- Enterprise 고객의 업무 중단
- 같은 현상 반복
- 고객이 계약 담당자 또는 임원 보고를 언급함

### 12.1 기술팀 에스컬레이션

다음 상황은 서비스 신뢰성팀 또는 엔지니어링 온콜로 전달한다.

- API 5xx 지속
- workflow execution queue 지연
- deployment 실행 실패
- webhook 수신 실패
- RAG 검색 인덱스 장애
- LLM provider 연동 장애
- 데이터베이스 연결 장애
- Redis 또는 queue 장애

### 12.2 고객성공팀 에스컬레이션

다음 상황은 고객성공 매니저에게 전달한다.

- Enterprise 고객의 SLA 문의
- 보상 또는 크레딧 요청
- 계약 위반 주장
- 고객 내부 임원 보고 필요
- 장기 장애 후 RCA 요청
- 고객 이탈 가능성 언급

### 12.3 보안팀 에스컬레이션

다음 상황은 보안 담당자에게 전달한다.

- 민감 데이터 노출 가능성
- 권한 우회 가능성
- 계정 탈취 가능성
- 감사 로그 위변조 의심
- 고객 API key 유출
- 비정상 대량 호출

## 13. 답변 초안 톤 가이드

고객 답변은 차분하고 명확해야 한다.

좋은 답변은 다음 특징을 가진다.

- 고객의 상황을 먼저 인정한다.
- 무엇을 확인할지 구체적으로 말한다.
- 필요한 정보를 간결하게 요청한다.
- 보상이나 책임을 단정하지 않는다.
- 다음 단계가 분명하다.

나쁜 답변은 다음 특징을 가진다.

- "문제 없습니다"라고 단정한다.
- 고객 책임을 먼저 언급한다.
- 내부 시스템 이름만 나열한다.
- 보상 금액을 확정한다.
- SLA 위반을 인정하거나 부정한다.
- 해결 예정 시간을 근거 없이 약속한다.

## 14. AI 분류 시 주의사항

AI는 고객 문의에서 다음 단어를 중요 신호로 본다.

긴급 신호:

- 긴급
- 장애
- 전체
- 프로덕션
- 운영 중단
- 고객 응대 중단
- 매출 손실
- 데이터 손실
- 데이터 노출
- 권한 오류
- SLA
- 보상
- 크레딧
- 환불
- 계약 위반
- 500
- webhook 실패
- workflow 실패
- 로그인 불가
- 결제 실패

일반 문의 신호:

- 사용법
- 방법
- 설정
- 문서
- 가이드
- 추천
- 가능 여부
- 개선 요청
- 가격 문의
- 교육 자료

단어 하나만으로 판단하지 말고 고객 플랜, 영향 범위, 장애 진행 여부, 업무 영향, 보상 언급 여부를 함께 본다.

## 15. 내부 처리 메모 예시

AI가 내부 메모를 생성할 수 있는 경우 다음 구조를 사용한다.

```json
{
  "severity": "P2",
  "sla_risk": "medium",
  "escalation_team": "customer-success",
  "required_information": [
    "organization_id",
    "workflow_id",
    "first_seen_at",
    "request_id"
  ],
  "do_not_confirm_compensation": true
}
```

단, 고객에게 반환하는 JSON이 `urgent`와 `draft_reply`만 요구되는 워크플로우라면 내부 메모 필드는 출력하지 않는다.

## 16. 최종 운영 원칙

고객지원 AI는 빠르게 분류하되 책임과 보상은 확정하지 않는다.

긴급도 true는 "즉시 확인 필요"를 의미한다. 긴급도 true가 곧 SLA 위반 확정이나 보상 확정을 의미하지 않는다.

SLA 위반 가능성이 있는 경우 고객에게는 검토 절차를 안내하고, 내부적으로는 고객성공팀 또는 서비스 신뢰성팀에 에스컬레이션한다.

보상안은 계약 조건, 장애 시간, 영향 범위, 고객 귀책 여부를 확인한 뒤 결정한다.

고객 문의가 불명확하면 긴급도는 보수적으로 판단하되, 답변 초안에는 추가 확인 정보를 요청한다.

이 문서는 AI 분류와 고객지원 초안 작성을 돕기 위한 기준이며, 최종 의사결정 권한은 담당 조직에 있다.
