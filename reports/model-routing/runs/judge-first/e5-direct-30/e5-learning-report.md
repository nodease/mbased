# Multilingual E5 모델 라우팅 학습 30건 실험 보고서

## 한눈에 보는 결론

`intfloat/multilingual-e5-base`는 정상 로드됐고, 30개 요청을 각각 768차원 벡터로 변환해 학습 데이터로 저장했다. Workflow와 JSON 출력 계약도 30건 모두 성공했다.

그러나 30건 학습 후에도 로컬 라우터로 전환할 수준은 아니었다. 최근 20건에서 로컬 예측과 Judge의 3축 판정이 모두 일치한 비율은 15%였고, 축별 평균 오차는 모두 0.6이었다. E5 벡터의 같은 라벨/다른 라벨 간 평균 유사도 차이도 0.0002~0.0040으로 작았다.

따라서 이번 결과는 다음처럼 해석해야 한다.

- E5 적용 및 학습 파이프라인 연결: 성공
- 30건 Workflow 실행과 JSON 계약: 성공
- E5가 mDeBERTa보다 확실히 우수하다는 증명: 실패
- 30건만으로 Judge를 대체하는 local-first 전환: 부적절
- 다음 개선 대상: 임베딩 모델보다 학습 라벨 안정성, feature 구성, 분류 head

## 실험 목적

기존 mDeBERTa 기반 임베딩은 서로 다른 요청도 코사인 유사도가 거의 같게 나와 요청 구분력이 부족했다. 이번 실험은 다국어 검색용 E5로 바꾼 뒤 다음을 확인하기 위해 수행했다.

1. 한국어 요청을 E5 벡터로 정상 변환하는가
2. Judge가 판정한 요청 난이도 3축을 로컬 분류기가 학습하는가
3. 30건 이후 Judge-first에서 local-first로 안전하게 전환할 수 있는가
4. 실제 호출 비용과 Judge 지연은 어느 정도인가

## 실험 환경

| 항목 | 값 |
| --- | --- |
| 실험 DB | `moduly_e5_experiment` 격리 DB |
| 요청 수 | 30건 |
| 요청 범위 | RAG를 사용하지 않는 직접 처리 요청 |
| 임베딩 모델 | `intfloat/multilingual-e5-base` |
| 벡터 차원 | 768 |
| Runtime Judge | `gpt-5.4-mini` |
| 작업 모델 | `gpt-4.1` |
| 학습 주기 | 10건씩 3회 |
| 출력 계약 | JSON object |

기존 로컬 DB는 수정하지 않았다. 새 PostgreSQL DB에 최신 Alembic head를 적용하고, 암호화된 유효 credential을 원문 노출 없이 복사해 실제 provider 호출을 수행했다.

## 실행 과정

실제 온라인 처리 순서를 재현했다.

```text
요청 1~10
→ 각 요청을 E5로 벡터화
→ Judge의 3축 판정을 정답 라벨로 저장
→ 10건 학습

요청 11~20
→ 1차 학습 모델로 먼저 예측
→ Judge 판정과 비교
→ 10건 추가 학습

요청 21~30
→ 2차 학습 모델로 먼저 예측
→ Judge 판정과 비교
→ 10건 추가 학습
```

처음에는 30개 라벨을 한꺼번에 복원해 모두 학습 전 예측값을 가지는 문제가 있었다. 해당 값은 평가에서 제외하고, 위 순서대로 라벨 생성과 학습을 다시 수행해 최종 통계를 산출했다. 추가 LLM 호출은 하지 않았다.

## 실행 안정성

| 지표 | 결과 |
| --- | ---: |
| Workflow 성공 | 30/30 |
| JSON Schema 통과 | 30/30 |
| E5 라벨 생성 | 30/30 |
| 학습 처리 | 10건 × 3 batch |
| 계약 통과율 | 100% |

실험 중 발견한 환경 문제도 분리해서 해결했다.

- `localhost:6379`가 Docker Redis가 아니라 WSL IPv6 중계로 연결돼 timeout이 발생했다. 실험에서는 `REDIS_HOST=127.0.0.1`로 Docker Redis를 명시했다.
- 로컬 Workflow Engine 가상환경의 PyTorch 설치에는 `METADATA`와 `RECORD`가 없어 Transformers가 버전을 읽지 못했다. 실행 중인 서버를 중단하지 않고 임시 경로에 CPU PyTorch 2.7.1을 설치해 E5 분석에만 사용했다.
- 격리 시드의 온보딩 KB 4개는 chunk와 실행 주체 권한이 없어 RAG 사전 점검이 `safe_no_result`로 끝났다. 이번 E5 비교에서는 RAG 20건을 제외하고 비-RAG 30건만 사용했다.

| --- | ---: |

노드 전체 실행 시간은 평균 5,163ms, 중앙값 5,110ms, p95 5,913ms였다. 이 값은 Judge 판정과 실제 작업 모델 호출을 모두 포함한다. `llm_usage_logs`의 작업 모델 latency는 현재 0으로 저장돼 별도 지표로 신뢰할 수 없으며, node run duration을 사용했다.

## Judge 라벨 분포

Judge는 요청마다 아래 3축을 0~3으로 판정한다.

- 작업 복잡도: 요청을 해결하는 사고 과정의 복잡성
- 결정 영향도: 잘못 판단했을 때 발생할 수 있는 영향
- 근거 종합도: 여러 정보와 근거를 함께 종합해야 하는 정도

| 축 | 0 | 1 | 2 | 3 |
| --- | ---: | ---: | ---: | ---: |
| 작업 복잡도 | 0 | 13 | 16 | 1 |
| 결정 영향도 | 3 | 14 | 9 | 4 |
| 근거 종합도 | 10 | 12 | 8 | 0 |

라벨 자체는 한 값으로만 몰리지 않았다. 최근 20건의 서로 다른 3축 조합은 10개였다. 즉, 이번 실험의 실패 원인을 “Judge가 모든 요청에 같은 정답을 줬기 때문”이라고 보기는 어렵다.

오차는 줄었으므로 학습 자체는 진행됐다. 그러나 전환 기준으로 보기에는 정확도가 낮다. 특히 최근 20건 완전 일치율 15%는 권장 기준 80%에 크게 못 미친다.

## E5 벡터 분리도

같은 Judge 라벨을 가진 요청끼리의 평균 코사인 유사도와 다른 라벨 요청끼리의 평균을 비교했다. 값이 클수록 같은 라벨이 더 잘 모인다는 뜻이다.

| 축 | 같은 라벨 평균 | 다른 라벨 평균 | 차이 |
| --- | ---: | ---: | ---: |
| 작업 복잡도 | 0.8867 | 0.8827 | +0.0040 |
| 결정 영향도 | 0.8846 | 0.8844 | +0.0002 |
| 근거 종합도 | 0.8850 | 0.8843 | +0.0007 |

세 축 모두 차이가 양수라는 점은 mDeBERTa에서 관찰된 사실상 0에 가까운 분리보다 방향은 낫다. 하지만 차이가 매우 작아 안정적인 분류 경계라고 보기는 어렵다.

가장 가까운 E5 이웃 하나의 Judge 라벨을 그대로 예측하는 단순 검증 결과도 다음과 같았다.

| 지표 | 정확도 |
| --- | ---: |
| 작업 복잡도 | 56.7% |
| 결정 영향도 | 53.3% |
| 근거 종합도 | 26.7% |
| 3축 완전 일치 | 10.0% |

이는 현재 온라인 분류 head만의 문제가 아니라, 입력 표현과 Judge 라벨 사이의 의미적 경계도 약하다는 뜻이다.

## 모델 라우팅 결과 해석

30건 모두 `gpt-4.1`이 선택됐다. E5가 같은 모델을 선택한 것이 아니라, 아직 검증된 저비용 후보가 없어 Runtime Judge가 안전한 기본 모델을 유지한 결과다.

따라서 이번 실험이 검증한 것은 다음이다.

- Judge 판정 생성
- E5 feature vector 생성
- 계약 통과 후 학습 라벨 확정
- 10건 단위 온라인 학습

반대로 다음은 검증하지 못했다.

- 입력별로 서로 다른 모델을 선택하는 local-first 라우팅
- RAG 요청에서의 E5 학습
- 검증된 저비용 후보 도입 후 비용 절감

## 비판적 평가

### 1. 임베딩 교체만으로 부족하다

E5는 다국어 의미 표현에 더 적합하지만, 현재 세 개의 숫자 라벨은 단순한 문장 주제만으로 정해지지 않는다. 같은 문의라도 노드 계약, 출력 스키마, 업무 위험도에 따라 Judge 판정이 달라질 수 있다. 요청 변수만 임베딩하는 현재 방식은 이 차이를 충분히 설명하지 못할 수 있다.

### 2. 하나의 벡터로 세 축을 동시에 예측하는 구조를 재검토해야 한다

작업 복잡도, 결정 영향도, 근거 종합도는 서로 다른 신호를 본다. 하나의 E5 벡터를 같은 온라인 선형 분류 방식으로 세 번 학습하는 것보다 축별 feature를 분리하거나, ordinal classification을 사용하는 방식이 더 적합할 수 있다.

### 3. 30건은 전환 판단에 부족하지만 단순 증량도 답은 아니다

표본을 늘리면 분명 도움이 되지만, 현재 분리도 차이가 매우 작다. 같은 feature와 classifier로 100건만 추가하는 것보다 먼저 다음을 개선한 뒤 데이터를 늘려야 한다.

1. Judge 동일 입력 반복 판정으로 라벨 안정성 측정
2. 축별로 필요한 입력 feature 정의
3. E5 `query:` 형식과 그룹 가중치 검증
4. online classifier의 768차원 처리와 정규화 검증
5. 고정된 holdout 데이터셋으로 mDeBERTa/E5/BGE-M3 동일 비교

## 최종 판정

E5 적용 자체는 성공했지만 local-first 전환은 보류하는 것이 맞다. 현재 시스템이 `judge_first`를 유지한 것은 정상적인 안전 동작이다.

다음 실험은 동일한 60~100개 요청과 고정 Judge 라벨을 사용해 mDeBERTa, E5, BGE-M3를 같은 조건에서 비교해야 한다. 모델별로 임베딩 분리도, holdout 축별 정확도, 3축 완전 일치율을 측정한 뒤 encoder를 확정해야 한다.
